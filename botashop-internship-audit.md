# Технический аудит проекта BotaShop

> Документ подготовлен на основе прямого чтения исходного кода репозитория (без домыслов). Цель — дать фактическую техническую базу для последующей подготовки документов по производственной практике (дневник, характеристика, отчёт, презентация). Все выводы опираются на конкретные файлы, классы и функции, указанные в скобках.

## 1. Project Summary

**BotaShop** — настольное (desktop) Windows-приложение для небольшого магазина (в коде фигурирует как «Детский магазин», см. `templates/base.html`), решающее задачу **создания и печати ценников** для товаров, а также ведения минимального каталога товаров.

Технически это **Django-приложение**, упакованное через **PyInstaller** в автономный `.exe`, и снабжённое **инсталлятором Inno Setup**. Приложение запускается двойным щелчком, поднимает локальный веб-сервер и открывает интерфейс в браузере пользователя — то есть по архитектуре это «desktop-приложение поверх веб-стека» (локальный Django + локальный FastAPI-агент печати).

**Бизнес-задача:** дать сотруднику магазина простой способ занести товар (название, цена) и мгновенно распечатать ценник нужного физического размера на подключённом принтере/этикет-принтере, без необходимости работать с Word/Excel/графическими редакторами.

**Предполагаемый пользователь:** продавец или администратор небольшого розничного магазина, без технических навыков, работающий на обычном Windows-ПК с локально подключённым принтером (в коде многократно фигурирует конкретная модель — **Xprinter XP-365B**, термопринтер этикеток).

**Основной пользовательский workflow:**
1. Открыть приложение (иконка на рабочем столе → браузер открывается автоматически на `http://127.0.0.1:8000/products/`).
2. Либо добавить товар (название + цена) через форму, либо воспользоваться разделом «Прямая печать» для разового ценника без сохранения в базу.
3. Выбрать принтер и размер ценника (список принтеров подтягивается автоматически из Windows).
4. Указать количество копий и нажать «Распечатать».

**Результат:** физически отпечатанный ценник заданного размера (по умолчанию 43×25 мм) с названием товара и ценой в тенге (₸), либо PDF-версия ценника, если используется обходной путь через браузерную печать.

## 2. Functional Requirements Implemented

### 2.1 Добавление товара в каталог
- **Что делает:** создаёт запись `Product` + связанный `ProductVariant` с ценами и авто-сгенерированным штрихкодом.
- **Как пользуется:** форма на `/products/create/` — вводится название, цена продажи, (опционально) закупочная цена.
- **Код:** `shop/views.py::product_create`, `shop/forms.py::ProductCreateForm`, `shop/services.py::create_product_with_variant_and_stock`.
- **Технологии:** Django Forms, Django ORM, `@transaction.atomic`.

### 2.2 Автогенерация штрихкода/артикула товара
- **Что делает:** при создании товара, если штрихкод не передан, подбирает следующий свободный числовой код, начиная с `2000000001`, инкрементируя последний использованный код с префиксом `200000`.
- **Код:** `shop/services.py::_generate_barcode`.
- **Технологии:** Django ORM (`filter().order_by().values_list().first()`).
- **Примечание:** это числовой идентификатор, хранящийся как текстовое поле `barcode`; графический штрихкод/QR нигде не рендерится (см. раздел 7).

### 2.3 Список товаров (каталог)
- **Что делает:** отображает все варианты товаров с категорией, брендом, размером, цветом, ценами, остатком (цветной бейдж) и штрихкодом; для каждой строки — кнопка перехода к печати.
- **Код:** `shop/views.py::product_list`, `templates/shop/product_list.html`.
- **Технологии:** Django QuerySet с `select_related`, Django template language.

### 2.4 Генерация ценника в формате PDF (фиксированный размер)
- **Что делает:** формирует PDF-страницу(ы) размером ровно 43×25 мм с названием товара (авто-перенос, авто-уменьшение шрифта) и ценой.
- **Как пользуется:** доступно через страницу предпросмотра `label_preview` → эндпоинт `print_label`.
- **Код:** `shop/label_service.py` (функции `generate_label_pdf`, `_draw_one_label`, `_wrap_to_lines`, `_greedy_wrap`).
- **Технологии:** `reportlab` (canvas, TTFont), `pypdf` (для внутренней самопроверки размера страницы).

### 2.5 Предпросмотр ценника перед печатью (PDF-путь)
- **Что делает:** открывает встроенный во вкладку PDF-просмотрщик браузера с уже сгенерированным ценником и автоматически вызывает системный диалог печати.
- **Код:** `shop/views.py::label_preview`, `templates/shop/label_preview.html`.
- **Технологии:** HTML `<object type="application/pdf">`, JavaScript (`window.print()`, `contentDocument`/`contentWindow`), CSS `@media print`.

### 2.6 Прямая печать через локального агента BotaPrint (production-путь)
- **Что делает:** рендерит ценник как растровое изображение (Pillow) и отправляет его напрямую в очередь печати Windows через GDI, минуя PDF и браузерную печать.
- **Как пользуется:** страница `print_settings.html` — выбор принтера/размера/копий, кнопка «Распечатать» шлёт `fetch()` прямо на локальный сервис `http://127.0.0.1:9100/print-label`.
- **Код:** `botaprint/main.py::print_label_endpoint`, `botaprint/printing.py::print_label`.
- **Технологии:** FastAPI, Pillow, `pywin32` (`win32print`, `win32ui`, `win32gui`, `win32con`).

### 2.7 «Прямая печать» без создания товара
- **Что делает:** позволяет распечатать разовый ценник (название + цена вручную), не создавая никаких записей в базе данных.
- **Код:** `shop/views.py::direct_print`, `shop/forms.py::DirectPrintForm`, `templates/shop/direct_print.html`.
- **Технологии:** Django Forms (кастомная валидация `clean_price`), `urllib.request` (серверный прокси-вызов к BotaPrint из Django-бэкенда).

### 2.8 Гибкая нормализация введённой цены
- **Что делает:** принимает цену в форматах `12990`, `12 990`, `12 990 ₸` (включая неразрывный пробел), очищает и превращает в `Decimal`, отклоняет отрицательные значения.
- **Код:** `shop/forms.py::DirectPrintForm.clean_price`.
- **Технологии:** Python `Decimal`, регулярные операции со строками.

### 2.9 Форматирование цены для отображения на ценнике
- **Что делает:** превращает число в целую часть с пробелами-разделителями тысяч и знаком ₸ (например, `12 500 ₸`).
- **Код:** дублируется в двух местах — `shop/label_service.py::_format_price` (PDF-путь) и `botaprint/printing.py::_format_price` (GDI-путь).
- **Технологии:** Python `'{:,}'.format(...)`.

### 2.10 Список принтеров Windows «на лету»
- **Что делает:** опрашивает Windows и возвращает все установленные принтеры с пометкой принтера по умолчанию.
- **Код:** `botaprint/printing.py::list_printers`, эндпоинт `botaprint/main.py::get_printers`.
- **Технологии:** `win32print.EnumPrinters`, `win32print.GetDefaultPrinter`.

### 2.11 Выбор физического размера ценника (7 форматов)
- **Что делает:** централизованный справочник поддерживаемых размеров этикетки — от 30×20 мм до 100×50 мм.
- **Код:** `botaprint/paper_sizes.py` (`SUPPORTED_LABEL_SIZES`, `DEFAULT_LABEL_SIZE`).
- **Технологии:** обычный Python-словарь, используемый и Django-формой, и FastAPI-сервисом.

### 2.12 Растровый рендеринг этикетки (без PDF)
- **Что делает:** рисует название товара и цену на белом Pillow-изображении нужного размера в пикселях, с авто-переносом текста на 2 строки и авто-подбором размера шрифта.
- **Код:** `botaprint/printing.py::render_label_image`, `wrap_text`, `fit_text`.
- **Технологии:** Pillow (`Image`, `ImageDraw`, `ImageFont`).

### 2.13 Точное позиционирование через Windows DEVMODE (калибровка размера бумаги)
- **Что делает:** формирует «частный» (per-job) `DEVMODE` для конкретного задания печати с произвольным размером бумаги (`PaperSize=DMPAPER_USER`), не трогая глобальные настройки принтера.
- **Код:** `botaprint/printing.py::build_job_devmode`, `assert_valid_devmode`.
- **Технологии:** `pywin32` (`win32print.DocumentProperties`, `win32print.GetPrinter`).

### 2.14 Временное изменение глобальных настроек принтера с гарантированным восстановлением (fallback-режим)
- **Что делает:** для принтеров, игнорирующих per-job DEVMODE (в коде указан именно Xprinter XP-365B), временно записывает нужный размер в глобальные настройки принтера через `SetPrinter`, печатает, и **всегда** восстанавливает исходные настройки в блоке `finally`, даже при ошибке печати.
- **Код:** `botaprint/printing.py::print_with_temporary_global_devmode`.
- **Технологии:** `pywin32` (`SetPrinter`, `GetPrinter`), `try/finally`.

### 2.15 Автоматическое центрирование ценника на физической странице
- **Что делает:** вычисляет прямоугольник назначения так, чтобы растр этикетки оказался ровно в физическом центре страницы принтера, с учётом непечатаемых полей устройства.
- **Код:** `botaprint/printing.py::_compute_dest_rect`, `_read_caps`.
- **Технологии:** `win32con.GetDeviceCaps` (PHYSICALWIDTH/HEIGHT/OFFSETX/OFFSETY).

### 2.16 Диагностика принтера (калибровочный эндпоинт)
- **Что делает:** возвращает DPI, физический размер страницы, печатаемую область и признак того, принял ли драйвер кастомный размер — без реальной печати.
- **Код:** `botaprint/main.py::debug_printer`, `botaprint/printing.py::get_printer_caps_with_job_devmode`.
- **Технологии:** FastAPI POST-эндпоинт + GDI device caps.

### 2.17 PNG-превью ценника без физической печати
- **Что делает:** рендерит этикетку в PNG и возвращает как HTTP-ответ, чтобы проверить макет без принтера.
- **Код:** `botaprint/main.py::preview_label`.
- **Технологии:** FastAPI `Response`, Pillow.

### 2.18 Проверка соединения с сервисом печати (health-check в UI)
- **Что делает:** индикатор на странице печати опрашивает `/health` BotaPrint и показывает статус («запущен»/«не запущен»).
- **Код:** JS-функция `checkAgent()` в `templates/shop/print_settings.html` и `templates/shop/direct_print.html`.
- **Технологии:** `fetch` API, CSS-классы статуса.

### 2.19 Django Admin для служебного доступа к данным
- **Что делает:** стандартная административная панель Django для просмотра/редактирования Category, Product, ProductVariant, StockMovement.
- **Код:** `shop/admin.py`.
- **Технологии:** `django.contrib.admin`.

### 2.20 Автоматическое применение миграций при запуске упакованного приложения
- **Что делает:** при каждом старте `.exe` программно выполняет `migrate --run-syncdb`, создавая/обновляя SQLite-базу без участия пользователя.
- **Код:** `launcher.py`.
- **Технологии:** `django.core.management.call_command`.

### 2.21 Единая точка запуска двух сервисов + защита от повторного запуска
- **Что делает:** поднимает Django (Waitress) и BotaPrint (Uvicorn) в двух потоках одного процесса, ждёт их готовности, открывает браузер; при повторном запуске `.exe` обнаруживает уже работающий экземпляр через именованный Mutex и просто открывает браузер повторно.
- **Код:** `launcher.py` (`_run_django`, `_run_botaprint`, `_wait_for`, Win32 Mutex-проверка).
- **Технологии:** `threading`, `ctypes.windll.kernel32.CreateMutexW`, `waitress`, `uvicorn`.

### 2.22 Логирование в файлы для диагностики без консоли
- **Что делает:** пишет отдельные лог-файлы (`launcher.log`, `django.log`, `botaprint.log`, `stdout.log`, `stderr.log`) в `%LOCALAPPDATA%\BotaShop\logs`, включая перехват `sys.stdout`/`sys.stderr`, которые равны `None` в windowed-сборке PyInstaller.
- **Код:** `launcher.py`.
- **Технологии:** модуль `logging`, `pathlib`.

### 2.23 Регрессионная самопроверка размера сгенерированного PDF
- **Что делает:** в debug-режиме, сразу после генерации PDF-ценника, повторно парсит его через `pypdf` и проверяет, что размер страницы не «случайно стал A4» (зафиксированный в коде исторический баг).
- **Код:** `shop/views.py::print_label` (блок `if __debug__`).
- **Технологии:** `pypdf.PdfReader`, `assert`.

## 4. Project Architecture

Проект состоит из **двух независимых процессов**, работающих на одной машине и общающихся по HTTP через `localhost`, плюс единой точки запуска (`launcher.py`), которая поднимает оба в потоках одного `.exe`.

```
Пользователь (браузер, http://127.0.0.1:8000)
        │
        ▼
Django (BotaShop)  — порт 8000, сервер Waitress
  ├── shop.views           ── HTTP-обработчики
  ├── shop.forms           ── валидация ввода
  ├── shop.services        ── бизнес-логика (создание товара, штрихкод)
  ├── shop.models (ORM)    ── Category / Product / ProductVariant / StockMovement
  ├── shop.label_service   ── генерация PDF-ценника (reportlab)
  └── templates/*.html     ── UI (Django Templates + inline CSS/JS)
        │
        │  (данные о товаре передаются в браузер через json_script)
        ▼
Браузер (JavaScript, fetch)
        │
        ▼
BotaPrint (FastAPI)  — порт 9100, сервер Uvicorn
  ├── main.py         ── HTTP API (/health, /printers, /print-label, /preview-label, /debug-printer)
  └── printing.py     ── рендеринг (Pillow) + печать (pywin32 GDI)
        │
        ▼
Windows Print Spooler → физический принтер (напр. Xprinter XP-365B)
```

**Путь данных пользователя (production-сценарий печати):**
1. Пользователь заполняет форму (`ProductCreateForm`) → `product_create` view → `services.create_product_with_variant_and_stock` → запись в SQLite через Django ORM.
2. Пользователь открывает `print_settings.html` для товара → браузер сам (JS) опрашивает BotaPrint (`/health`, `/printers`).
3. По нажатию «Распечатать» браузер отправляет `fetch POST` **напрямую** на `http://127.0.0.1:9100/print-label`, **минуя Django**.
4. BotaPrint валидирует запрос (Pydantic + ручные проверки) → `printing.print_label` → строит DEVMODE → создаёт GDI DC → `render_label_image` (Pillow) → печатает через `ImageWin.Dib.draw`.

**Альтернативный путь (без БД, через Django-прокси):** форма `direct_print.html` → Django `direct_print` view → `urllib.request` к BotaPrint `/print-label` **с сервера** (не из браузера) → тот же движок печати.

**Альтернативный путь (PDF + браузерная печать, фактически legacy/fallback):** `product_list` → `print_settings` → `label_preview` view → `print_label` view генерирует PDF через `label_service.generate_label_pdf` (reportlab) → отображается в `<object>` → печатается системным диалогом браузера.

**Django-структура (MVT):**
- **Models** (`shop/models.py`): 4 модели, ORM отвечает за весь доступ к данным.
- **Views** (`shop/views.py`, functions-based, без class-based views и без DRF): 6 view-функций.
- **Templates** (`templates/`): базовый layout + 5 страниц приложения `shop`.
- **Forms** (`shop/forms.py`): 2 формы с кастомной валидацией.
- **Services** (`shop/services.py`): выделенный слой бизнес-логики, отделённый от views (паттерн "fat services, thin views").
- **Static** (`staticfiles/`): содержит только стандартные ассеты Django Admin, собранные `collectstatic`; собственных CSS/JS-файлов проект не содержит — вся стилизация и скрипты — inline в шаблонах.

## 6. Database

**Тип БД:** SQLite (`django.db.backends.sqlite3`), единый файл `db.sqlite3`.

**Расположение:** и в режиме разработки, и в собранном `.exe` путь вычисляется одинаково — `%LOCALAPPDATA%\BotaShop\data\db.sqlite3` (`config/settings.py`). Это осознанное архитектурное решение: база никогда не хранится ни внутри папки установки (`Program Files`), ни внутри временной распаковки PyInstaller (`sys._MEIPASS`), а всегда в профиле пользователя — благодаря этому переустановка/обновление приложения не уничтожает данные.

### Модели / таблицы (`shop/models.py`)

**Category** («Категория»)
| Поле | Тип | Описание |
|---|---|---|
| name | CharField(100), unique | Название категории |

**Product** («Товар»)
| Поле | Тип | Описание |
|---|---|---|
| name | CharField(200) | Название товара |
| category | ForeignKey → Category, `SET_NULL`, nullable | Категория (необязательна) |
| brand | CharField(100), blank | Бренд |
| created_at / updated_at | DateTimeField (auto) | Служебные метки времени |

**ProductVariant** («Вариант товара») — конкретная продаваемая единица (SKU) товара
| Поле | Тип | Описание |
|---|---|---|
| product | ForeignKey → Product, `CASCADE` | Родительский товар |
| size | CharField(20), blank | Размер |
| color | CharField(50), blank | Цвет |
| sku | CharField(100), blank | Артикул |
| barcode | CharField(50), unique, blank | Штрихкод (генерируется автоматически) |
| purchase_price | DecimalField(10,2) | Закупочная цена |
| selling_price | DecimalField(10,2) | Цена продажи (печатается на ценнике) |
| current_stock | PositiveIntegerField, default 0 | Остаток на складе |
| created_at / updated_at | DateTimeField (auto) | Служебные метки времени |

**StockMovement** («Движение товара») — журнал складских операций
| Поле | Тип | Описание |
|---|---|---|
| variant | ForeignKey → ProductVariant, `CASCADE` | К какому варианту относится |
| type | CharField, choices: IN / OUT / WRITE_OFF / RETURN | Тип движения (Приход/Расход/Списание/Возврат) |
| quantity | PositiveIntegerField | Количество |
| purchase_price | DecimalField(10,2), nullable | Цена на момент операции |
| comment | TextField, blank | Комментарий |
| created_at | DateTimeField (auto) | Дата операции |

**Связи:** Category 1→N Product (SET_NULL при удалении категории), Product 1→N ProductVariant (CASCADE), ProductVariant 1→N StockMovement (CASCADE).

**Важное наблюдение:** модель `StockMovement` **спроектирована**, зарегистрирована в admin и присутствует в миграциях, но **ни один view или сервис в проекте её не создаёт и не читает** — то есть складской учёт заложен в схему данных, но соответствующий UI/бизнес-логика (приход/списание товара) не реализованы. Это стоит формулировать как «в проекте спроектирована модель данных для учёта складских движений» — не как «реализован модуль учёта склада».

**CRUD-операции, реально задействованные в коде:**
- **Create:** `Product.objects.create()`, `ProductVariant.objects.create()` — только в `services.create_product_with_variant_and_stock`.
- **Read:** `ProductVariant.objects.select_related(...).order_by(...)` в `product_list`; `get_object_or_404` в нескольких views.
- **Update / Delete:** отсутствуют в пользовательском интерфейсе приложения; доступны только через стандартный Django Admin (`/admin/`), автоматически предоставляемый фреймворком.

**Миграции:** 3 файла, управляются стандартным механизмом Django (`shop/migrations/0001_initial.py`, `0002_alter_productvariant_color_alter_productvariant_size.py`, `0003_alter_category_options_alter_product_options_and_more.py`). Миграции только аддитивные/уточняющие (изменение `blank=True` для полей, локализация `verbose_name` на русский) — деструктивных изменений схемы нет.

**Обращение к БД:** исключительно через Django ORM, никакого «сырого» SQL в проекте не найдено.

## 7. Price Label Functionality

Это центральная функция проекта, и в репозитории она реализована **двумя параллельными механизмами**, которые важно не путать в отчёте.

### 7.1 Откуда берутся данные
- Для товара из каталога: поля `ProductVariant.product.name` (название) и `ProductVariant.selling_price` (цена продажи).
- Для разовой «прямой печати»: значения вводятся вручную в форме `DirectPrintForm` и никуда не сохраняются.

### 7.2 Поля, попадающие на ценник
Только два: **название товара** и **цена продажи**. Дополнительные поля (бренд, размер, цвет, штрихкод, остаток) **на сам ценник не выводятся** — они используются только в табличном представлении каталога (`product_list.html`).

### 7.3 Штрихкод / QR
В проекте **нет генерации графического штрихкода или QR-кода** — ни в PDF-пути, ни в GDI-пути. Это явно задокументировано в исходном коде: `shop/label_service.py` — «No barcode on the label», `botaprint/printing.py` — «no barcode» в архитектурном комментарии. Поле `barcode` в модели используется только как уникальный текстовый идентификатор товара (аналог внутреннего SKU), отображаемый текстом в таблице каталога.

### 7.4 Размеры ценников
Два независимых источника истины (важная деталь для отчёта):
- **PDF-путь (`shop/label_service.py`):** жёстко зафиксированный единственный размер — **43 × 25 мм** (константы `LABEL_W_MM`, `LABEL_H_MM`). Параметра выбора размера в этом модуле нет.
- **GDI-путь (`botaprint/paper_sizes.py`):** справочник из 7 форматов — `30×20`, `43×25` (по умолчанию), `58×30`, `58×40`, `58×60`, `75×120`, `100×50` мм — выбираемых пользователем в интерфейсе.

### 7.5 Форматирование цены
Целое число, разряды разделены пробелом, суффикс `₸`: например `12 500 ₸`. Реализовано дважды (по разу на каждый механизм печати) — `label_service._format_price` и `printing._format_price`, логика идентична (`'{:,}'.format(int(price)).replace(',', ' ') + ' ₸'`).

### 7.6 Вёрстка (layout) содержимого этикетки
Общий для обоих путей принцип:
1. Название товара — жирный шрифт, по центру, **автоматический перенос максимум на 2 строки**.
2. Если название не помещается в 2 строки при стартовом размере шрифта — **размер шрифта итеративно уменьшается**, пока не влезет (`_wrap_to_lines` в PDF-пути, `fit_text` в GDI-пути).
3. Цена — жирный шрифт фиксированного размера, по центру, ниже названия с заданным отступом.
4. Вертикальное позиционирование рассчитывается так, чтобы блок «название + отступ + цена» был центрирован по высоте с небольшим смещением (40% свободного пространства — под ценой, для визуального баланса; задокументировано в комментариях `label_service.py`).

### 7.7 HTML/CSS в формировании ценника
Сам ценник **не рисуется через HTML/CSS** — это программная отрисовка через `reportlab` (векторный PDF) либо через `Pillow` (растровое изображение). HTML/CSS используются только для **интерфейса управления печатью** (страницы настроек, кнопки, статус-баннеры), а не для содержимого самого ценника.

### 7.8 Генерация PDF vs изображения
- **PDF:** `reportlab.pdfgen.canvas.Canvas`, векторная графика, шрифт регистрируется как TrueType (`pdfmetrics.registerFont`), страница создаётся с точным размером в pt, пересчитанным из мм (`reportlab.lib.units.mm`).
- **Изображение (растр):** `PIL.Image.new('RGB', (w_px, h_px), 'white')` + `ImageDraw` — точный размер в пикселях вычисляется из физического размера в мм и DPI принтера, полученного через Windows GDI (`LOGPIXELSX`/`LOGPIXELSY`).

### 7.9 Шрифты
Оба механизма поддерживают кириллицу, казахские буквы и знак ₸ через один и тот же приоритет поиска шрифта:
1. `DejaVuSans-Bold.ttf` (если положен разработчиком в `fonts/` или `botaprint/fonts/`);
2. `C:\Windows\Fonts\segoeuib.ttf` (Segoe UI Bold);
3. `C:\Windows\Fonts\arialbd.ttf` (Arial Bold);
4. Резерв — встроенный `Helvetica-Bold` reportlab (только PDF-путь) или `ImageFont.load_default()` (только GDI-путь).

### 7.10 Preview
- **PDF-путь:** предпросмотр = сам итоговый PDF, показанный во встроенном просмотрщике браузера (`label_preview.html`).
- **GDI-путь:** отдельный эндпоинт `POST /preview-label`, возвращающий PNG «как будет напечатано» — без обращения к принтеру (`botaprint/main.py::preview_label`). Именно этим способом, судя по сохранённым файлам `preview.png`, `preview_43x25.png`, `preview/label_preview_30x20_text_offset.png`, проверялась вёрстка в процессе разработки.

### 7.11 Полный pipeline создания ценника (production-путь, GDI)

```
Данные (название, цена)
   → выбор размера (SUPPORTED_LABEL_SIZES) и принтера
   → POST /print-label (FastAPI, Pydantic-валидация)
   → build_job_devmode()      — DEVMODE 43×25мм (или иной выбранный размер)
   → _create_printer_dc()     — печатный DC Windows с этим DEVMODE
   → render_label_image()     — Pillow-растр (имя + цена, авто-перенос/авто-шрифт)
   → _compute_dest_rect()     — координаты центрирования на физической странице
   → ImageWin.Dib(img).draw() — блит растра напрямую в очередь печати
   → физический ценник на принтере
```

## 8. Printing

**Что печатается:** растровое изображение размером ровно с выбранный формат этикетки (по умолчанию 43×25 мм), содержащее только название товара и цену — без каких-либо служебных элементов (без рамок, логотипов, штрихкодов).

**Каким образом (два независимых механизма):**

1. **Прямая печать через Windows GDI (основной, "production" путь).** Django/браузер не участвуют в самом акте печати — HTTP-запрос уходит на локальный сервис BotaPrint (FastAPI на порту 9100), который:
   - открывает принтер (`win32print.OpenPrinter`);
   - строит "частный" DEVMODE с нужным размером бумаги (`build_job_devmode`) либо, если это принтер, помеченный как игнорирующий per-job DEVMODE (в коде — Xprinter XP-365B), **временно подменяет глобальный DEVMODE** через `SetPrinter`, печатает и восстанавливает исходные настройки (`print_with_temporary_global_devmode`);
   - создаёт печатный `DC` (`win32ui`/`win32gui.CreateDC`);
   - рисует Pillow-изображение и передаёт его на устройство через `ImageWin.Dib.draw()` внутри `StartDoc`/`StartPage`/`EndPage`/`EndDoc`.
   - **PDF-файлы и сторонние вьюеры (например SumatraPDF) не используются** — это прямо задокументировано в `botaprint/main.py` и защищено регрессионным тестом `botaprint/tests.py::TestNoSumatraPDF`, который грепает исходный код на отсутствие следов такого подхода (что указывает на отказ от более раннего варианта реализации в пользу прямой GDI-печати).

2. **Печать через браузер (fallback/legacy путь).** Django генерирует PDF (`reportlab`) фиксированного размера 43×25 мм, показывает его в `<object type="application/pdf">`, и через JavaScript автоматически вызывает `window.print()` (или `print()` встроенного PDF-вьюера) спустя ~900 мс после загрузки. Здесь фактическую отправку на принтер и выбор масштаба/ориентации выполняет сам браузер и операционная система — приложение не управляет процессом печати напрямую.

**Параметры печати, реально поддерживаемые:**
- **Размер этикетки:** выбор из 7 предустановленных форматов (GDI-путь) либо фиксированный 43×25 мм (PDF-путь).
- **Количество копий:** от 1 до 100 в обоих путях (валидируется и на клиенте, и на сервере).
- **Принтер:** выбирается из списка, полученного напрямую от Windows (`win32print.EnumPrinters`); принтер по умолчанию помечается автоматически.
- **Ориентация:** для GDI-пути реализована защитная логика авто-поворота растра на 90°, если драйвер печатает в другой ориентации, чем ожидалось (только в неактивном сейчас, "чистом" per-job режиме, поскольку по умолчанию включён fallback-режим `print_with_temporary_global_devmode`, где ориентация всегда `DMORIENT_PORTRAIT`).

**Ограничения, зафиксированные в коде:**
- BotaPrint принимает соединения **только с `127.0.0.1`** (не публикуется в сеть); CORS явно ограничен адресами `127.0.0.1:8000` и `localhost:8000` (`botaprint/main.py`).
- Реализация ориентирована на конкретную модель термопринтера (Xprinter XP-365B), для которой в коде включён специальный обходной путь — то есть надёжность на других моделях принтеров не гарантирована и не покрыта тестами на реальном оборудовании (юнит-тесты используют моки Windows API).
- Максимум 100 копий за одно задание (жёстко ограничено валидацией).

## 9. User Interface

Интерфейс — набор классических серверных Django-страниц (без SPA-фреймворка), с общим layout `templates/base.html` (тёмная навигационная панель, светлый фон, карточки, таблицы).

### Экран 1 — Список товаров (`/products/`, `product_list.html`)
- **Назначение:** обзор всего каталога.
- **Элементы:** таблица (товар, категория, бренд, размер, цвет, закупочная/продажная цена, остаток в виде цветного бейджа, штрихкод, кнопка «Распечатать»); кнопка «+ Добавить товар».
- **Действия пользователя:** переход к добавлению товара или к печати конкретного варианта.
- **После действия:** переход на соответствующую страницу (`product_create` или `print_settings`).

### Экран 2 — Добавление товара (`/products/create/`, `product_create.html`)
- **Назначение:** ввод нового товара.
- **Элементы:** форма (название, цена продажи, закупочная цена — необязательно), кнопки «Сохранить»/«Назад».
- **Действия:** отправка формы (POST).
- **После действия:** при успехе — flash-сообщение об успехе и редирект на список; при ошибке — та же страница с подсвеченными ошибками полей.

### Экран 3 — Настройки печати существующего товара (`/products/<id>/print/`, `print_settings.html`)
- **Назначение:** печать ценника для конкретного товара напрямую через BotaPrint.
- **Элементы:** статус-баннер соединения с BotaPrint (обновляется автоматически при загрузке страницы), выпадающий список принтеров (заполняется JS из `/printers`), выбор размера этикетки, поле количества копий, кнопка «Распечатать», кнопка «Обновить список принтеров».
- **Действия:** нажатие «Распечатать» → `fetch POST` напрямую в BotaPrint.
- **После действия:** блок сообщения `#print-msg` показывает результат (успех/ошибка) без перезагрузки страницы; кнопка блокируется на время запроса.

### Экран 4 — Прямая печать (`/direct-print/`, `direct_print.html`)
- **Назначение:** разовый ценник без сохранения товара.
- **Элементы:** обычная Django-форма (название, цена, принтер — `<select>`, размер, количество), статус-баннер BotaPrint.
- **Действия:** обычная отправка формы (полный POST на сервер, без AJAX для самой печати — AJAX используется только для списка принтеров).
- **После действия:** сервер вызывает BotaPrint и возвращает страницу с flash-сообщением об успехе/ошибке; выбранный принтер сохраняется при повторном показе формы после ошибки валидации.

### Экран 5 — Предпросмотр PDF-ценника (`/products/<id>/label/preview/`, `label_preview.html`)
- **Назначение:** визуальная проверка PDF-версии ценника и запуск системной печати.
- **Элементы:** тулбар (кнопка «Распечатать», информация о товаре/количестве/размере, кнопка «Назад»), встроенный PDF-вьюер на всю страницу.
- **Действия:** просмотр PDF; печать (авто-вызов диалога печати браузера при загрузке, либо вручную по кнопке).
- **После действия:** открывается системный диалог печати браузера.

**Технические детали UI:**
- Формы валидируются как на клиенте (базовые HTML-атрибуты `min`/`max`/`required`), так и обязательно на сервере (Django Forms / Pydantic).
- Модальных окон нет — все переходы полностраничные либо через AJAX-обновление отдельных блоков.
- Responsive-вёрстка минимальна (простой `max-width`/`grid`), явных медиа-запросов для мобильных экранов нет — интерфейс рассчитан на десктопный браузер.
- Безопасность передачи данных в JS реализована через `{{ value|json_script:"id" }}` — Django-механизм, исключающий XSS при встраивании серверных данных в `<script>`.

## 11. Important Algorithms and Technical Solutions

**1. Авто-перенос и авто-уменьшение шрифта названия товара.** Реализовано дважды независимо — как векторный вариант (`_greedy_wrap` + `_wrap_to_lines` в `label_service.py`, измерение через `canvas.stringWidth`) и как растровый вариант (`wrap_text` + `fit_text` в `printing.py`, измерение через `draw.textbbox`). Алгоритм жадный (greedy word-wrap): слова добавляются в текущую строку, пока не превышен максимум ширины; если после переноса получилось больше 2 строк — размер шрифта уменьшается на 1pt, и перенос выполняется заново, пока текст не уложится в 2 строки или размер не достигнет минимального порога.

**2. Расчёт вертикальной компоновки этикетки.** Название и цена не просто центрируются — используется формула распределения «свободного пространства» с весом 40% под ценой (`price_y = max(_MARGIN, free * 0.40)`), что визуально смещает блок текста немного вверх от геометрического центра — сознательное дизайнерское решение, отражённое в комментариях кода.

**3. Формирование «частного» (per-job) DEVMODE для нестандартного размера бумаги.** Использует последовательность `DocumentProperties(DM_OUT_BUFFER)` → модификация полей `PaperSize/PaperWidth/PaperLength/Orientation` → `DocumentProperties(DM_IN_BUFFER|DM_OUT_BUFFER)` для валидации драйвером. Код явно обрабатывает недокументированную особенность `pywin32`, когда функция может вернуть либо новый объект `PyDEVMODE`, либо целое число (модификация "по ссылке") — и никогда не путает эти два случая (`assert_valid_devmode`).

**4. Временная подмена глобальных настроек принтера с гарантированным откатом.** Для принтеров, игнорирующих per-job DEVMODE, применяется паттерн "save → mutate → act → restore" с двумя вложенными `try/finally`, что гарантирует восстановление исходных настроек принтера даже при исключении в процессе печати — важное техническое решение для защиты пользовательской системы от побочных эффектов.

**5. Центрирование растра на физической странице принтера.** Через `GetDeviceCaps` считываются физический размер страницы и офсеты непечатаемой области, после чего вычисляется прямоугольник назначения так, чтобы этикетка оказалась в геометрическом центре реального листа/ленты, а не просто в углу координат DC.

**6. Автоматическое определение DPI и вычисление размера растра в пикселях.** Вместо фиксированных «магических» размеров изображение генерируется под фактический DPI принтера (`LOGPIXELSX`/`LOGPIXELSY`), считанный динамически, что делает рендеринг переносимым между разными принтерами без ручной перекалибровки.

**7. Нормализация пользовательского ввода цены.** `DirectPrintForm.clean_price` принимает несколько разговорных форматов написания цены (с пробелами, с неразрывными пробелами, со знаком ₸) и надёжно приводит их к `Decimal`, отклоняя некорректные и отрицательные значения.

**8. Регрессионная защита от «PDF стал A4».** В `shop/views.py::print_label`, под `if __debug__`, только что сгенерированный PDF немедленно перечитывается через `pypdf`, и через `assert` проверяется, что его физический размер не близок к A4/Letter — задокументированная защита от конкретного ранее случавшегося дефекта.

**9. Единый event loop для ASGI-сервера в неглавном потоке.** В `launcher.py` `uvicorn.Server` запускается вручную (не через `uvicorn.run()`), с отключённой установкой обработчиков сигналов ОС (`server.install_signal_handlers = lambda: None`) и собственным `asyncio`-циклом — обход ограничения Windows/Python, запрещающего вызов `signal.signal()` вне главного потока.

**10. Единая точка правды для физических размеров этикеток.** `botaprint/paper_sizes.py` — весь остальной код (форма Django, FastAPI-модели, движок печати) читает размеры только оттуда, что исключает рассинхронизацию значений между слоями.

## 12. Validation and Error Handling

**На уровне Django-форм:**
- `ProductCreateForm`: обязательность полей, ограничение длины названия (200 символов), корректность числового формата цены — с русскоязычными сообщениями об ошибках.
- `DirectPrintForm`: аналогичная валидация плюс кастомный `clean_price()` (см. раздел 11, п.7) и ограничение количества копий диапазоном 1–100.

**На уровне FastAPI (BotaPrint):**
- Автоматическая типовая валидация через Pydantic-модели (`PrintRequest`, `PreviewRequest`, `DebugPrinterRequest`).
- Дополнительные ручные бизнес-проверки внутри `print_label_endpoint`: непустое имя принтера, непустое и не длиннее 200 символов название товара, цена ≥ 0, копии в диапазоне 1–100 — каждая со своим кодом ответа (400) и русскоязычным сообщением.
- Различение «принтер не найден» (404) от прочих ошибок печати (500) по содержимому текста исключения.

**На уровне Django-view `direct_print` (интеграция с внешним сервисом):**
- Раздельная обработка `urllib.error.HTTPError` (разбор JSON-тела ошибки от BotaPrint), `urllib.error.URLError` (сообщение «BotaPrint не запущен») и произвольного `Exception` (логирование полного traceback через `logger.exception`, показ пользователю общего сообщения).

**На уровне низкоуровневой печати (`botaprint/printing.py`):**
- `RuntimeError` с русскоязычным, понятным пользователю текстом на каждом критичном шаге (принтер не найден, не удалось создать контекст печати, не удалось сформировать изображение, ошибка отправки задания).
- `assert_valid_devmode()` — защитная проверка типа объекта DEVMODE перед использованием, предотвращающая труднодиагностируемые сбои глубоко внутри вызовов GDI.
- Гарантированное восстановление глобальных настроек принтера в `finally`-блоке даже при исключении в процессе печати (описано в разделе 11).
- В launcher — если BotaPrint не поднялся за 25 секунд, приложение **не завершает работу**, а продолжает работать в режиме "только каталог товаров, без печати", информируя пользователя через `MessageBoxW`.

**Возможные исключения, предусмотренные в коде:** `ImportError` (отсутствие `pywin32`/`win32print` — обрабатывается явной проверкой и понятным сообщением «pywin32 не установлен»), сетевые ошибки при обращении Django→BotaPrint, ошибки конвертации цены (`InvalidOperation`, `ValueError` из `Decimal`), таймаут HTTP-запроса (`timeout=15` в `urllib.request.urlopen`).

## 13. Application Build

Процесс полностью автоматизирован скриптом `build.bat` и выполняется в следующей фактической последовательности:

1. **Проверка окружения:** `python --version` — сборка прерывается, если Python не найден в PATH.
2. **Установка/обновление зависимостей:**
   - `pip install --upgrade pip`;
   - `pip install -r requirements.txt` (Django-часть);
   - `pip install -r botaprint/requirements.txt` (агент печати);
   - `pip install waitress whitenoise pyinstaller` (дополнительно нужные для сборки/деплоя, но не входящие в основной `requirements.txt`).
3. **Сбор статики Django:** `python manage.py collectstatic --noinput --clear` — обязательный шаг, так как в production (`WhiteNoise` + `CompressedManifestStaticFilesStorage`) статика должна быть физически собрана заранее, `runserver`-режим для этого не используется.
4. **Очистка предыдущих сборок:** удаление `dist\BotaShop` и `build\BotaShop`, если существуют.
5. **PyInstaller-сборка (`onedir`):** `pyinstaller BotaShop.spec --clean --noconfirm`.
   - Точка входа — `launcher.py` (а не `manage.py`!), то есть в один исполняемый пакет собираются сразу оба сервиса — и Django, и BotaPrint (последний импортируется как обычный Python-модуль внутри процесса, а не запускается как отдельный `.exe`).
   - В бандл включаются: `templates/`, `shop/migrations/` (нужны Django в runtime), `botaprint/fonts/`, локали и админ-шаблоны самого Django (обязательны, поскольку `sys._MEIPASS` подменяет базовую директорию), а также собранная `staticfiles/`.
   - Явно прописан большой список `hiddenimports`, поскольку статический анализ PyInstaller не всегда обнаруживает динамические импорты Django/FastAPI/Starlette/Uvicorn/Waitress/WhiteNoise/pywin32/Pillow/ReportLab/pypdf/pydantic.
   - Явно исключены неиспользуемые тяжёлые пакеты (`psycopg2`, `tkinter`, `matplotlib`, `numpy`, `scipy`, `pandas`) для уменьшения размера бандла.
   - Собирается **windowed**-приложение (`console=False`) — конечный пользователь не видит консольного окна.
   - UPX-компрессия применяется с исключениями для критичных бинарников (`vcruntime140.dll`, `python3*.dll`, `pywintypes*.dll`, `win32ui.pyd`, `win32print.pyd`), поскольку их сжатие UPX может ломать работу.
6. **Проверка результата:** скрипт явно проверяет наличие `dist\BotaShop\BotaShop.exe` и прерывается с ошибкой, если файла нет.
7. **Поиск Inno Setup 6** по типовым путям установки (`Program Files`, `Program Files (x86)`, `C:\InnoSetup6`); если не найден — сборка не прерывается, а просто пропускает шаг создания инсталлятора, оставляя готовым PyInstaller-бандл.
8. **Компиляция инсталлятора:** `ISCC.exe BotaShopSetup.iss` → `dist\BotaShopSetup.exe`.

**Что попадает в `dist/`:** папка `dist\BotaShop\` (весь `onedir`-бандл — `BotaShop.exe` + служебная папка `_internal` со всеми Python-зависимостями и данными) и, при наличии Inno Setup, финальный `dist\BotaShopSetup.exe`.

**Запуск после сборки:** пользователь запускает `BotaShop.exe` (напрямую или через установленный инсталлятором ярлык) → выполняется логика `launcher.py`, описанная в разделах 2.20–2.22 и 15.

*В репозитории на момент аудита папки `dist/BotaShop/` и `build/` уже присутствуют и заполнены — то есть сборка через `build.bat`/PyInstaller была фактически выполнена в этом окружении как минимум один раз.*

## 14. Installer

**Файл:** `BotaShopSetup.iss` — скрипт **Inno Setup 6**.

**Что делает:**
- Определяет метаданные приложения: `AppName=BotaShop`, `AppVersion=1.0.0`, фиксированный `AppId` (GUID) — согласно комментарию в файле, менять его после первого релиза нельзя, иначе переустановка будет воспринята как новое приложение.
- Устанавливает приложение в `{autopf}\BotaShop` (аналог `Program Files`), без требования прав администратора (`PrivilegesRequired=lowest`, с возможностью переопределения из командной строки).
- Требует 64-битную Windows (`ArchitecturesAllowed=x64compatible`).
- Язык инсталлятора — русский (`compiler:Languages\Russian.isl`).

**Какие файлы включает:** весь каталог `dist\BotaShop\*` рекурсивно (`Source: "dist\BotaShop\*"; DestDir: "{app}"; Flags: ignoreversion recursesubdirs createallsubdirs`) — то есть инсталлятор упаковывает именно результат PyInstaller-сборки, а не исходный код.

**Ярлыки:** создаёт пункт в меню «Пуск» всегда; ярлык на рабочем столе — опционально, по пользовательской галочке (`Tasks: desktopicon`, `Flags: checkedonce`).

**Как создаётся `Setup.exe`:** компиляцией `BotaShopSetup.iss` через `ISCC.exe` (см. раздел 13, шаг 8) с LZMA2-компрессией максимального уровня (`Compression=lzma2/ultra64`, `SolidCompression=yes`).

**Что получает конечный пользователь:** единый файл `BotaShopSetup.exe`, после запуска которого мастер установки (на русском языке) копирует приложение в выбранную папку, по желанию создаёт ярлыки и предлагает сразу запустить BotaShop (`Flags: nowait postinstall skipifsilent`).

**Отдельное продуманное решение:** секция `[UninstallDelete]` удаляет **только** папку установки (`{app}`), но никогда не упоминает `%LOCALAPPDATA%\BotaShop` — это гарантирует, что база данных и логи пользователя переживают удаление или обновление приложения; данное решение явно прокомментировано в самом `.iss`-файле.

## 15. Deployment / Distribution

Фактически реализованный в проекте путь передачи приложения конечному пользователю:

```
Исходный код (Django + FastAPI-агент, шаблоны, миграции)
   → build.bat: установка зависимостей + collectstatic
   → PyInstaller (BotaShop.spec, onedir, entry point launcher.py)
   → dist/BotaShop/BotaShop.exe   (автономный бандл, Python не нужен на целевой машине)
   → Inno Setup (BotaShopSetup.iss)
   → dist/BotaShopSetup.exe        (единый файл-инсталлятор)
   → передача файла пользователю (например, копированием/флешкой/скачиванием — сам механизм передачи в проекте не определён)
   → запуск BotaShopSetup.exe на целевом ПК → мастер установки → BotaShop.exe в Program Files
   → первый запуск BotaShop.exe: миграции применяются автоматически, поднимаются Django (порт 8000) и BotaPrint (порт 9100), открывается браузер
   → последующие запуски: Mutex-проверка обнаруживает уже работающий экземпляр (если есть) и просто открывает браузер
```

Отдельно в проекте предусмотрен **альтернативный путь распространения только агента печати** — `botaprint/BotaPrint.spec` позволяет собрать `BotaPrint.exe` как самостоятельный исполняемый файл (см. `botaprint/README.md`, раздел «Упаковка в BotaPrint.exe»). Это может использоваться, например, для развёртывания агента печати отдельно от основного приложения на другом ПК в локальной сети — хотя в текущей `launcher.py`-реализации оба сервиса объединены в один процесс/`.exe`.

Требования к целевой машине для установленного приложения (по совокупности файлов): 64-разрядная Windows, установленный драйвер соответствующего принтера; сам Python на целевой машине не требуется — все зависимости уже вморожены в бандл PyInstaller.

## 16. Development Challenges

*(Формулировки намеренно нейтральные — как факт устройства проекта, а не как личный опыт автора, если это не может быть подтверждено кодом.)*

- В проекте решена задача **упаковки Django-приложения в desktop-исполняемый файл** без изменения кода приложения под "особый" режим — через универсальный расчёт `BASE_DIR`/данных, работающий как в режиме разработки, так и внутри распакованного PyInstaller-бандла (`sys._MEIPASS`).
- В проекте решена задача **раздачи статических файлов Django без выделенного веб-сервера** — через WhiteNoise, что необходимо, поскольку конечное приложение не разворачивается за Nginx/Apache.
- В проекте решена задача **сохранения пользовательских данных (SQLite-базы) отдельно от кода приложения и от временной директории распаковки PyInstaller**, чтобы обновление/переустановка не приводили к потере данных — реализовано через единый путь `%LOCALAPPDATA%\BotaShop\data`.
- Реализация требует учитывать, что **при `console=False` (windowed-сборке PyInstaller) `sys.stdout`/`sys.stderr` равны `None`**, что ломает библиотеки, ожидающие файлоподобные объекты (в частности, `uvicorn.logging`) — в проекте это решено ручным перенаправлением потоков в лог-файлы.
- Реализация требует учитывать, что **`signal.signal()` в Python на Windows нельзя вызывать вне главного потока** — что критично, поскольку `uvicorn.run()` по умолчанию пытается установить обработчики сигналов; в проекте это обойдено явным конструированием `uvicorn.Server` и отключением `install_signal_handlers`.
- В проекте решена задача **корректной физической печати нестандартного размера бумаги через Windows GDI**, включая случаи, когда драйвер конкретного принтера игнорирует per-job `DEVMODE` — потребовалось реализовать альтернативный механизм с временным изменением и гарантированным восстановлением глобальных настроек принтера.
- Реализация учитывает **недокументированные особенности `pywin32`** (функция `DocumentProperties` может возвращать как объект `DEVMODE`, так и целое число, в зависимости от переданных аргументов и версии) — добавлена явная защитная проверка типа (`assert_valid_devmode`).
- В проекте решена задача **точного позиционирования содержимого этикетки** — как в PDF (векторные координаты reportlab), так и в растре (пиксельные координаты с учётом фактического DPI устройства и физического офсета непечатаемой области).
- В истории проекта прослеживается **отказ от промежуточного PDF+сторонний PDF-принтер (SumatraPDF) в пользу прямой растровой печати через GDI** — зафиксировано отдельным регрессионным тестом, который проверяет отсутствие следов такого подхода в коде.
- В проекте решена задача **создания единого дистрибутива** (инсталлятор Inno Setup), корректно разделяющего то, что должно удаляться при деинсталляции (файлы программы), и то, что должно сохраняться (пользовательские данные).
- Реализация учитывает необходимость **одновременного запуска синхронного WSGI-приложения (Django/Waitress) и асинхронного ASGI-приложения (FastAPI/Uvicorn) в одном процессе** — решено через параллельные потоки с раздельными event loop.

## 17. Skills Demonstrated

- **Python-разработка (backend):** реализация двух взаимодействующих сервисов (Django-приложение и отдельный FastAPI-микросервис) с чётким разделением зон ответственности.
- **Django (полный MVT-стек):** модели с внешними ключами и `Meta`-опциями (`shop/models.py`), формы с кастомной валидацией (`shop/forms.py`), function-based views (`shop/views.py`), выделенный сервисный слой (`shop/services.py`), система шаблонов с наследованием (`templates/`), стандартный `admin`.
- **Проектирование базы данных:** нормализованная схема из 4 связанных таблиц (Category → Product → ProductVariant → StockMovement) с корректными типами полей (`DecimalField` для денег, `PositiveIntegerField` для количеств) и продуманными `on_delete`-стратегиями (`SET_NULL` vs `CASCADE`).
- **Работа с СУБД и миграциями:** последовательные миграции Django, отслеживающие эволюцию схемы (добавление `blank=True`, локализация `verbose_name`).
- **Разработка REST/HTTP API:** проектирование FastAPI-эндпоинтов с типизированными Pydantic-схемами запросов (`botaprint/main.py`).
- **Frontend без фреймворков:** построение рабочего интерфейса на чистом HTML/CSS/JavaScript, включая асинхронные запросы (`fetch`), безопасную передачу данных сервер→клиент (`json_script`) и динамическое обновление DOM.
- **Генерация документов/графики программным путём:** формирование PDF через `reportlab` (векторная графика, работа со шрифтами, координатами) и растровых изображений через `Pillow`.
- **Низкоуровневая интеграция с Windows API:** прямая работа с `pywin32` (GDI-контексты устройств, `DEVMODE`, очередь печати), включая обход недокументированных особенностей библиотеки.
- **Отладка сложных системных проблем:** написание и использование выделенных диагностических скриптов (`debug_printer_sizes.py`, `debug_setprinter_fallback.py`) для локализации проблем печати на конкретном оборудовании до их исправления в основном коде.
- **Тестирование:** написание модульных тестов с использованием `unittest.mock` для изоляции кода от реального Windows-оборудования (`botaprint/tests.py`), включая регрессионные тесты, защищающие от повторения прошлых ошибок.
- **Упаковка и дистрибуция приложений (packaging):** конфигурирование PyInstaller (`.spec`-файлы, `hiddenimports`, `datas`, исключения пакетов, UPX) для создания автономного исполняемого файла из веб-приложения.
- **Создание инсталляторов:** написание скрипта Inno Setup с учётом требований к сохранности пользовательских данных при обновлении/удалении.
- **Автоматизация сборки:** написание оркестрирующего batch-скрипта (`build.bat`), последовательно выполняющего установку зависимостей, сборку статики, компиляцию и упаковку.
- **Работа с многопоточностью и асинхронностью в одном процессе:** совместный запуск синхронного и асинхронного серверов с ручным управлением event loop.
- **Локализация:** весь пользовательский интерфейс, тексты ошибок и инсталлятор — на русском языке, с корректной обработкой денежной единицы ₸ и кириллицы/казахских букв в шрифтах.

Назначение: единая точка входа для собранного приложения.

Что реализовано: установка без прав администратора, ярлыки, сохранение пользовательских данных при удалении/обновлении.
